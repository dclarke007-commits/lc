The job to be done

Three revenue leaks, one that earns real engineering

Inquiry leak — people ask but never get booked (phone tag). → tokenized links, QR, approval queue, inquiry logging.
Rebooking leak — one-time jobs never repeat. → one-tap rebook + post-job nudge.
Lapse leak — regulars quietly go cold. → cadence-derived "gone cold" flag.
Payment float — ~$500/mo unpaid, untracked. → cash ledger + reminder.

Underneath it's CRUD over a small relational model. The single place that earns real engineering is one invariant:

Never double-book the last open slot. (NFR4)

That's why the stack choice was about corpus & tooling gravity, not capability — every candidate handles a transaction. The engineering lives in how capacity is committed.

Design paradigm

Server-first full-stack

RSC renders every surface · Server Actions are the only mutation entry point · Postgres is the single source of truth. No separate API tier, no client-side store.

Dependency direction: surfaces → actions → domain → db. Nothing lower imports upward; nothing bypasses actions to reach the DB from a surface. This one choice pre-decides a huge slab.

The crux

Capacity has exactly one owner — commitBooking()

All three write paths funnel through one function that re-checks both caps inside a single locked transaction. Two cap-checkers = the double-book bug.

  • Serverless-safe lock (AD-3): SELECT … FOR UPDATE / pg_advisory_xact_lock — never session-scoped advisory locks (they silently break under Neon/Supabase transaction-mode pooling).
  • One predicate (AD-2): consumesSlot() — booked/completed/no-show consume, cancelled releases. Both commit and dashboard read it.
  • Override (FR39) is a flag into commitBooking, never a bypass. Pending requests aren't Jobs (AD-4).

Data model — the seed

Canonical rows; everything else is derived on read

Every row carries owner_id — filter present from v1 (AD-8). Metric-critical fields: Job.created_at, completed_at, overridden; MessageLog.drafted_at vs dispatched_at. Gone-cold, room-left, repeat-rate & counter-metrics are all computed on read (AD-7) — no stored flags, no cron.

The other half of the contract

What we're deliberately not building

  • Auto-send messages — draft + tap only; adapter seam (AD-5) lets it slot in later.
  • Card / auto-charge — cash + ledger + reminder; no processor surface.
  • Multi-cleaner logic — only the owner_id seam is planted (AD-8).
  • Clock-time slots — per-day caps are enough to decide accept/pass.
  • Native app — phone-web + the operator's own WhatsApp/SMS.
  • Materialized metrics / cron — derive-on-read until it stops being cheap (AD-13).
  • APM / observability stack — platform logs + typed action results.
  • Ads / lead-gen — the problem is a demand leak, not a drought.

Positioning holds throughout: most tools help you run jobs; this one helps you not lose them.

Suggested build order

Spine → capacity core → surfaces outward

  1. Schema + Operator seed — Drizzle model, owner_id everywhere, one-row operator (AD-8).
  2. Capacity core — commitBooking + consumesSlot + the locked transaction (AD-2/3/12). This is where the one real bug lives; build and test it first.
  3. Lifecycle — Job state machine (AD-10), then the ledger on top.
  4. Client surfaces — token links + public/QR + approval queue (AD-6/4/11).
  5. Derive + dashboard — gone-cold, room-left, metrics, counter-metrics (AD-7).
  6. Compose + delivery — templates → MessageDraft → deep-link adapter (AD-5).
