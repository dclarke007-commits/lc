- (decision) Stack: Next.js 16 (App Router + Server Actions, RSC) + Postgres (Neon/Supabase) via Drizzle ORM, deployed on Vercel. Binds: language=TS, runtime, data store, deploy target. Prevents: units picking incompatible frameworks/ORMs/hosting. Chosen for largest AI-agent corpus + tooling gravity for a solo+AI build. Web-verified 2026-07: Next 16.x stable, App Router/Server Actions default.
- (version) Next.js 16.x (App Router, Server Actions, DevTools MCP for agents); Rails 8 considered as one-person-framework alt and set aside. Verified via web 2026-07-15.
- (decision) Paradigm: server-first full-stack. RSC renders, Server Actions mutate, Postgres is single source of truth. Binds: all writes go through a Server Action; no separate API tier; no client-side data store; nothing client-side touches the DB. Prevents: units inventing REST endpoints or client caches that fork the write path.
- (decision) Capacity single-owner (NFR4 crux): one commitBooking() re-checks per-day cap + weekly-14 inside a single locked Postgres transaction and commits-or-rejects. All three slot-consuming paths funnel through it: client-confirm (FR7), operator approve-from-queue (FR36), operator direct (FR39). Override (FR39) is a flag INTO commitBooking, never a bypass. Binds: the only code that inserts a capacity-consuming Job. Prevents: two cap-checkers racing = double-book.
- (decision) Concurrency mechanism: commitBooking serializes concurrent claims on the last slot via a Postgres lock keyed to the operator schedule (advisory lock on owner_id, or SELECT FOR UPDATE on the day record) with both caps re-checked inside the tx. Rule: exactly one winner on the last open slot; the rest get no-availability (NFR4).
- (decision) Approval queue (FR6/FR36): pending new-client requests do NOT reserve or consume capacity. Capacity is consumed only at approval, where commitBooking's cap check re-runs. First approval wins; remaining pending requests on that slot are surfaced as no-longer-available. Known clients (per-client link, FR7) skip the queue and commit directly.
- (decision) Messaging compose != deliver (addendum B): a composition layer turns (client, slot, amount, template) into a channel-agnostic MessageDraft{recipient, body, type}; a delivery adapter renders it to a wa.me/sms: deep-link in v1. Binds: templates depend only on MessageDraft, never on the transport. Prevents: transport details leaking into templates. Future auto-send = new adapter, no rework. Dispatch logged at the boundary (FR21).
- (decision) Auth/token = capability: operator is a single authenticated session (FR33); client links are signed, unguessable tokens (NFR6) - per-client token is client-scoped, one public token, QR encodes the public token URL (FR5). No client login (FR34). Binds: a bearer can do exactly what its token scopes. Prevents: a per-client link acting as a public one or vice versa.
- (decision) Derived-on-read: a single derive module computes expectedNextDate, goneCold, roomLeft, day-maxed, and all dashboard metrics from canonical Client/Job rows on every render. No stored flags, no cron, no background job. gone-cold is a view-time computation surfaced when the operator opens the dashboard. Binds: one definition per derived value. Prevents: two modules computing gone-cold or repeat-rate differently.
- (decision) Tenancy seam: every Client/Job/token/inquiry/message row carries an owner_id FK, hardcoded to the single operator in v1. No tenant-scoping logic and no multi-user auth in v1. Binds: the column exists from day one. Prevents: a schema rewrite + backfill when Vision multi-cleaner arrives (it becomes add-scoping, not re-model).
- (decision) Time model: timestamps stored UTC; all capacity, cadence, and week math computed in the operator's single local timezone. Week boundary for the 14-cap is Monday-Sunday local (FR1). Binds: one tz source for all schedule arithmetic. Prevents: cap/cadence math drifting between UTC and local.
- (decision) Operational envelope: deploy on Vercel with preview + production environments; managed Postgres (Neon or Supabase) whose managed backups satisfy durability (NFR5). Data export (FR35) is a Server Action streaming the owner's Client/Job rows as CSV. Secrets via Vercel env; no self-hosted infra in v1.
- (constraint) Capabilities are fixed by the finalized PRD (41 FRs, 7 NFRs) + addendum; the spine implements them literally and does not re-open scope. NFR7: no structure ships that does not serve a named leak or a capacity/cash decision.
