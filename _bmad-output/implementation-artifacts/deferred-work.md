## Deferred from: code review of story-1.3 (2026-07-16)

- **zonedWallToUtc drops milliseconds when measuring offset** — offset is computed at whole-second precision (`Date.UTC(...second)` omits ms), so a caller passing `ms≠0` gets a result off by up to 999ms. Latent — every current caller passes `ms=0`. Fix when a sub-second boundary caller lands. [lib/domain/clock.ts:75-83]
- **Redundant non-unique `owner_id` index** — `capacity_settings_owner_id_idx` is fully covered by the unique `capacity_settings_owner_uq` on the identical single column; pure write-amplification. Dropping needs a new migration. [lib/db/schema.ts + drizzle/0003]
- **Clock helpers throw RangeError on unvalidated tz** — none of the exported clock functions validate `tz`; an unknown zone throws from Intl. Latent now (stored tz is validated at write). Ensure Story 1.4 and later consumers only pass the validated stored tz, or add a typed guard. [lib/domain/clock.ts:28]
- **Timezone free-text on phone-first surface** — `timezone` renders as `<input type="text">`; typing an exact IANA name on a phone is error-prone (invalid only surfaces after a round-trip). A zero-JS `<select>` of common zones better fits NFR1. [app/(operator)/settings/page.tsx]

## Deferred from: code review of story-1.4 (2026-07-16)

- **Pool starvation under a large same-day booking burst** — `commitBooking` runs inside `db.transaction()`, which pins one of `max:10` pool connections for the whole txn including while blocked on `pg_advisory_xact_lock`. With ≥10 concurrent same-(owner,week) claims, all connections pin (one working, rest blocked) and other requests (reads, settings) starve/queue. Not a deadlock (drains one-by-one). Single-operator realistic concurrency is double-submits (≤2), so deferred; revisit with multi-device or `pg_try_advisory_xact_lock` + bounded retry if it ever bites. [lib/domain/capacity.ts]
- **Cross-week same-nonce concurrent submits → opaque booking-failed** — after the lock is re-keyed to `(owner, week-monday)`, two concurrent submits carrying the SAME idempotency nonce but dates in DIFFERENT weeks take different locks, both insert, and the loser hits `job_owner_idempotency_uq` → caught as generic `booking-failed` instead of an idempotent replay. Near-impossible because the nonce is a per-render random UUID (never legitimately reused across weeks); could be closed by catching the unique-violation and re-reading the existing job. [lib/domain/capacity.ts]

## Deferred from: code review of story-1.5 (2026-07-16) — ✅ RESOLVED by Story 1.6

Story 1.6 (cancel/reschedule) owned capacity-on-correction and CLOSED both items in the lifecycle whitelist (commit for 1.6): D1 — `completed→booked` removed (`completed` now only → `cancelled`, AD-10 quote-exact); D2 — resurrection `no-show|cancelled → booked` removed (both terminal `[]`), so the domain now fails closed instead of re-consuming a slot without a cap recheck. `booked→cancelled` (the AD-10 Task-1 gap) was also added. Reachable only by a hand-crafted POST now that the Undo button is gone. **1.6 fix:** drop `'booked'` from `completed`'s targets so lifecycle matches AD-10 exactly. [lib/domain/lifecycle.ts:45-50]
- **D2 — resurrection `no-show|cancelled → booked` skips the cap/weekly-ceiling recheck (keystone bug)** — moving a terminal job back to `booked` re-consumes a slot (`consumesSlot(booked)` is true), but `transition()` does the completion write with NO capacity/ceiling validation, so a resurrection can push a week over its cap or the global weekly ceiling — the exact invariant Story 1.4 enforces on the forward path. Reachable only by hand-crafted POST now (Undo button removed). **1.6 fix:** route resurrection through the same cap+ceiling check as `commitBooking` (capacity-on-correction), then re-expose a safe correction/reschedule UI. Also add the AD-10 `booked→cancelled` transition (spec Task 1) that 1.5 left out of the whitelist. [lib/domain/lifecycle.ts + lib/domain/capacity.ts]

## Deferred from: code review of story-1.7 (2026-07-16)

- **Redundant owner resolution in `getDashboardCapacity`** — the action resolves the owner twice (`getOwnerCapacity()` resolves internally, then a separate `getOwnerId()`), two round-trips per render on a dynamic uncached surface. Wasteful today; latent risk that if a later story adds a real owner SOURCE, config and jobs could read for two different owners with nothing tying them together. Collapse to one resolved `ownerId` when that source lands (needs a `getCapacityConfig(ownerId)` that does not re-resolve). [app/(operator)/actions.ts:57-65]
- **Consuming job on a now-non-working day is invisible in the day table** — `weekConsuming` sums all 7 Mon–Sun days, but the `weekCapacity` day loop skips non-working weekdays. If the operator drops a weekday from `workingDays` while a consuming job already sits on it, that job still lowers `roomLeft`/`consuming` but shows in no rendered day row — an unlocatable unit of capacity. Requires a config change over an existing booking, hence rare. Fix: include any day with consuming jobs even if now non-working. [lib/domain/derive.ts weekConsuming vs weekCapacity]
