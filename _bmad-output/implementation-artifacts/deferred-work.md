## Deferred from: code review of story-1.4 (2026-07-16)

- **Pool starvation under a large same-day booking burst** — `commitBooking` runs inside `db.transaction()`, which pins one of `max:10` pool connections for the whole txn including while blocked on `pg_advisory_xact_lock`. With ≥10 concurrent same-(owner,week) claims, all connections pin (one working, rest blocked) and other requests (reads, settings) starve/queue. Not a deadlock (drains one-by-one). Single-operator realistic concurrency is double-submits (≤2), so deferred; revisit with multi-device or `pg_try_advisory_xact_lock` + bounded retry if it ever bites. [lib/domain/capacity.ts]
- **Cross-week same-nonce concurrent submits → opaque booking-failed** — after the lock is re-keyed to `(owner, week-monday)`, two concurrent submits carrying the SAME idempotency nonce but dates in DIFFERENT weeks take different locks, both insert, and the loser hits `job_owner_idempotency_uq` → caught as generic `booking-failed` instead of an idempotent replay. Near-impossible because the nonce is a per-render random UUID (never legitimately reused across weeks); could be closed by catching the unique-violation and re-reading the existing job. [lib/domain/capacity.ts]

## Deferred from: code review of story-3.1 (2026-07-16)

- **✅ RESOLVED 2026-07-16 (code-review of story-3.2) — DECISION D1: per-client token revocation is now durable.** Added a per-link random `nonce` column (migration `0009`), folded into the signed HMAC payload (`clientToken.ts`: `ClientTokenClaims.nonce`, `generateTokenNonce`, sign+verify), so the token is no longer a pure function of `{clientId, ownerId, capability}`. `ensureClientToken` is now READ-OR-CREATE: it returns the stored link verbatim (stable URL) — and if that value no longer verifies (rotated `CLIENT_TOKEN_SECRET`), re-signs with the SAME persisted nonce and refreshes the row (heals rotation, preserving 3.1 review-P1). A deleted row can never be resurrected: `revokeClientToken` deletes it, and a later re-mint generates a FRESH nonce → a NEW value, so the leaked link stays dead. Added explicit domain API `rotateClientToken` (issue a new link, kill the old) + `revokeClientToken`, `resolveTokenClaims` now enforces `row.nonce === claims.nonce`. Tests: `booking-token.test.ts` (heal, rotate-reissue, revoke-durability) + `clientToken.test.ts` (nonce varies → new token; nonce-less token rejected). **Story 3.3 may now hand per-client links to real clients.** _Original entry:_ token was a deterministic HMAC with no nonce/version, so a re-mint resurrected a revoked/leaked URL. [lib/domain/booking.ts + lib/auth/clientToken.ts + lib/db/queries.ts + token schema/migration 0009]
- **DECISION D2 — client slot horizon is the current operator-week only.** `resolveBookingView` renders `weekCapacity` for today's Mon–Sun week; a saturated week shows an empty list + a single non-bookable `nextOpen` text pointer. Documented Gap-#5 dev decision (consistent with 1.7 nearest-open), but a client viewing late in a full week sees little to book against NFR2 "book in seconds." Revisit if a multi-week horizon is wanted (Story 3.2 booking flow will inform this). [lib/domain/booking.ts:resolveBookingView, app/book/[token]/page.tsx]
- **NULL `client_id` does not enforce one live public token** — `token_owner_client_capability_uq` on `(owner_id, client_id, capability)`; Postgres treats NULL `client_id` as distinct, so multiple `book-public` rows per owner can coexist and `upsertClientToken`'s conflict target won't dedupe them. Not exercised in 3.1 (`book-client` always sets `client_id`). Fix when Epic 4's public token lands: partial unique index `WHERE client_id IS NULL` on `(owner_id, capability)`, or `NULLS NOT DISTINCT`. [lib/db/schema.ts token indexes / drizzle 0007]
- **No expiry on client tokens (by-design long-lived)** — unlike the operator session's HMAC-covered `exp`, `ClientTokenClaims` carries no `exp`; a leaked link is valid until revoked. No longer compounded by D1 (resolved above): a leaked link can now be killed on demand via `revokeClientToken`/`rotateClientToken`. Add an optional `exp` claim only if a time-boxed link lifetime becomes a requirement. [lib/auth/clientToken.ts ClientTokenClaims]
- **Token payload is readable (not opaque)** — `base64url(JSON{clientId,ownerId,capability}).hmac` exposes the internal client/owner UUIDs to whoever holds the link (the bearer is already authorized for that client). Unforgeable (HMAC), matches the operator session token model — accepted. True opacity would need the random-token-with-server-side-claims model (declined). Flag only. [lib/auth/hmac.ts]
