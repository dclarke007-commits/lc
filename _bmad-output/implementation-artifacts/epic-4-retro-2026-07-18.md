# Epic 4 Retrospective — Client Self-Booking (Plug the Inquiry Leak)

Date: 2026-07-18 · Stories: 4-1, 4-2, 4-3, 4-4 (all done) · Tests: 292 green · PRs #3, #4 merged

## What shipped
The stranger→booking pipeline: a public signed link + printable QR (4-1) → a new-client submit that creates a provisional client + a capacity-holding-nothing `PendingRequest` + one deduped `link` inquiry (4-2) → an operator approval queue that converts a request into a real booking via `commitBooking` (4-3) → manual inquiry logging with a source + the pure conversion-denominator dedup (4-4). FR4, FR5, FR6, FR36, FR37 covered.

## What went well
- **The Epic-3 token seam paid off.** 4-1/4-2 reused the HMAC + durable-nonce revocation surface wholesale — the public path was a thin, fail-closed extension, not new crypto.
- **`commitBooking` as the single capacity keystone (AD-2) held.** 4-3 got one-winner concurrency, cap re-check, and idempotency for free by routing approval through it — zero re-implemented capacity logic, zero new locks.
- **Two invariants kept the design honest end-to-end:** AR5 (a request holds no capacity) and AR12 (one `link` inquiry per visit session). Both were stated in each spec and asserted in tests, so "no phantom holds" and "no double-counted inquiry" were provable, not hoped.
- **The 4-lens review bar earned its cost.** It caught real defects the tests missed: the 4-2 whole-submission idempotency gap (duplicate provisional clients on double-tap), and the 4-3 non-atomic approve (stranded provisional client + phantom-booking-on-decline-race). Both were MED, both would have been production bugs.

## What was hard / what we learned
- **Idempotency scope is subtle.** 4-2 first coupled the whole submission to the inquiry dedup, which silently dropped a legitimate different-day resubmit (review F1). The fix — split keys: request idempotency on `(owner, nonce, date)`, inquiry dedup on `(owner, nonce)` — is the reusable lesson: **key each effect on its own natural identity, not a borrowed one.**
- **Non-atomic multi-write actions strand state.** 4-3's approve did commit → status-flip → client-promote as three separate writes; a fault mid-sequence stranded the client. The self-healing fix (elect-winner-first, resume on `approved`, roll back on capacity failure) is the pattern to reach for whenever an action spans an external-ish call (commitBooking) plus local state.
- **Public writes widen the attack surface fast.** 4-2/4-4 accept stranger/operator free-text; the guards that mattered were input length caps, the `link`-source server-only whitelist, and owner-from-token-not-form. All caught in security review, none obvious from the happy path.

## Accepted limitations (logged as action items)
1. **Manual `logInquiry` double-submit** inflates the conversion denominator (no dedup key). Accepted for single-operator v1; Epic 6's FR24 dashboard should dedupe manual double-logs (or add a per-render submit nonce + partial index).
2. **No rate limiting on public writes** (4-2 submit, 4-4 log) — LOCKED accepted gap. Add per-IP throttle + provisional-row cap before multi-tenant / lower-trust.
3. **`getOwnerId()` binds the singleton operator, not `session.sub`** — safe under the single-operator invariant; must source owner from the verified session before a second operator ships (latent multi-tenant risk flagged in 4-3 security review; same note applies app-wide).
